## 1. Назначение документа

Документ связывает функциональные области проекта с текущими автотестами и
потенциальным покрытием. Он показывает не только то, что уже автоматизировано,
но и следующие проверки, которые можно реализовать после уточнения требований.

Статусы:

- ✅ `AUTO` — автотест реализован и входит в текущий набор.
- 📝 `TODO` — кандидат на автоматизацию.
- ❓ `SPEC` — перед автоматизацией нужно уточнить ожидаемое поведение продукта.
- ⚠️ `FLAKY` — тест реализован, но требует стабилизации.

Приоритеты:

- `P0` — безопасность или критический сценарий, блокирующий работу пользователей.
- `P1` — основная бизнес-функция, ошибка заметно влияет на работу.
- `P2` — важный дополнительный сценарий или удобство пользователя.
- `P3` — низкий риск, визуальные и редкие граничные случаи.

## 2. Стратегия автоматизации

Для проекта применяется сочетание `Testing Trophy` и `Risk-Based` подходов:

- API/Integration — позитивные, негативные, граничные и контрактные проверки;
- E2E — критические пользовательские пути и связь UI с backend;
- Visual — внешний вид ключевых страниц и состояний;
- Accessibility — базовая доступность интерактивных элементов;
- дорогие и редкие проверки не должны дублироваться на UI, если их дешевле и
  точнее проверить через API.

Теги природы проверки описывают, что именно проверяется:

- `@smoke` — критический happy path;
- `@regression` — расширенный регресс;
- `@negative` — ошибочные данные или запрещённое действие;
- `@boundary` — граничные значения;
- `@security` — авторизация, роли и чувствительные данные;
- `@schema` — контракт ответа API;
- `@data-driven` — один сценарий с несколькими наборами данных;
- `@visual` — визуальная регрессия;
- `@a11y` — доступность.

Теги расписания описывают, когда запускать проверку:

- `@ci-gate` — критическая проверка, которая должна блокировать merge;
- `@regression` — полный регрессионный или ночной запуск.

Сейчас в коде используются теги HTTP-методов `@POST`, `@GET`, `@PUT`,
`@DELETE`. Остальные теги — целевое улучшение и добавляются вместе с TODO-тестами.

## 7. Профили запуска

Текущее поведение GitHub Actions:

- полный набор запускается на `push`, `pull_request` и вручную;
- используется один worker из-за ограничения стенда `429 Too many requests`;
- локально ретраев нет, в CI разрешено до двух ретраев;
- screenshot сохраняется при падении, trace — на первом ретрае;
- результаты уходят в Allure Report, Allure TestOps и Telegram.

Целевая схема после внедрения тегов:

| Профиль | Состав | Назначение |
|---|---|---|
| PR / merge gate | `P0`, `@smoke`, `@security`, `@schema`, `@ci-gate` | Быстрая проверка критических рисков |
| Полный regression | Все API и E2E `@regression` | Ручной или ночной запуск |
| Visual / a11y | `@visual`, `@a11y` | Отдельный неблокирующий запуск |

## 9. Правила актуализации

- Новый сценарий сначала добавляется в дерево как `TODO` или `SPEC`.
- После реализации статус меняется на `AUTO`, добавляются файл и стабильный ID.
- Для неизвестных границ нельзя придумывать ожидаемые значения: сначала
  фиксируется требование, затем создаётся тест.
- Проверка размещается на самом дешёвом уровне, который подтверждает нужный риск.
- Критический happy path можно дополнительно покрыть E2E, даже если есть API-тест.
- После изменения покрытия сверяются суммы UI, API и общий результат команды
  `npx playwright test --list`.
- Изменение состава тестов и стратегии запуска фиксируется в release notes.
